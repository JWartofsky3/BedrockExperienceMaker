# Local database

`schema.sql` is the authoritative MySQL 8.0+ schema for the local development database. It creates the `bedrock_experience_maker` database when imported.

Primary keys are UUID strings generated by the application. They identify our catalog records, releases, manifest packs, and experience-pack revisions. Minecraft manifest `header.uuid` and module UUID values are stored as ordinary indexed attributes only—they are never unique constraints because creators may reuse them.

The schema stores source URLs, manifest data, checksums, and file inventories. It does not store `.mcaddon` archives or serve downloads.

## Availability and compatibility policy

Providers often expose only the newest downloadable artifact. `addon_release_sources.availability_status` therefore records what a curator can currently obtain; a historical catalog release may remain useful in a previously published plan even when its download is no longer available.

Minecraft version information is advisory. `addon_release_compatibility_evidence` retains where a version statement came from (manifest minimum, provider tag, creator claim, curator test, or user report) and its assessment. The UI should show warnings for questionable or mismatched versions, not reject the add-on or the experience pack. An experience-pack revision can optionally record its intended Bedrock version to make those warnings meaningful.

## Core relationship map

```text
addon ──< addon_source
  │
  └──< addon_release ──< addon_release_source
             │
             └──< release_pack ──< module / dependency / capability / file inventory

experience_pack ──< experience_pack_revision ──< experience_pack_item >── addon_release
```

`display_order` is the order shown to a creator. If combined archive export is ever implemented, lower order values are merged first and higher values are merged later; therefore the item at the top of the UI should be assigned the highest merge precedence explicitly by the exporter rather than relying on a database row order.
